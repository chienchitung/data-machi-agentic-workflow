想像一個場景：使用者問「這個季度 Q3 的客訴工單有多少件，對應的 SLA 定義是什麼，目前有哪些相關 Trello 卡片正在處理？」這個問題需要同時查詢工單系統、Confluence 文件庫與 Trello 看板三個完全獨立的資料來源。如果 Agent 按順序逐一執行，每個工具即使只花 2 秒，三個加起來就是 6 秒以上。但如果三個查詢同時發出，整體只需要等最慢的那一個。

## 順序執行 vs. 平行執行

```text
【順序執行】
[查工單 2s] → [查 Confluence 2s] → [查 Trello 2s]
總耗時：約 6 秒

【平行執行】
[查工單 2s] ─┐
[查 Confluence 2s] ─┼─ 同時發出
[查 Trello 2s] ─┘
總耗時：約 2 秒
```

平行執行的核心價值是：**讓彼此獨立的查詢同時進行，把累加等待變成並行等待。**

## 什麼情況可以平行？

<CardGroup cols={2}>
  <Card title="可以平行" icon="check">
    - 同時查詢工單統計、文件定義與看板狀態
    - 同時搜尋多個獨立知識庫
    - 同時呼叫不互相依賴的外部 API

    判斷標準：A 的結果不需要作為 B 的輸入。
  </Card>

  <Card title="必須保持順序" icon="xmark">
    - 先查正式專案代號，再用代號查 Trello
    - 先取得 user ID，再用 ID 查工單
    - 先建立資料，再更新關聯

    判斷標準：B 的參數需要從 A 的結果取得。
  </Card>
</CardGroup>

## 混合情況：部分平行、部分順序

```text
步驟 1：查詢使用者基本資料，取得 user_id 與 project_id
          │
          ▼
步驟 2 ──┬── 用 user_id 查工單歷史
          ├── 用 project_id 查 Trello
          └── 查通用 SLA 文件
                    │
                    ▼
步驟 3：彙整三個來源結果
```

在 LangGraph 中，這種結構可以透過 fan-out（一個節點拆成多個平行路徑）和 fan-in（多個路徑匯合到一個節點）實現。

## Data Machi 的實作方式

```python
import asyncio
from langchain_core.messages import ToolMessage

async def action_node(state: AgentState):
    tool_calls = state["messages"][-1].tool_calls

    tasks = [
        execute_tool_async(tool_call)
        for tool_call in tool_calls
    ]

    results = await asyncio.gather(*tasks, return_exceptions=True)

    tool_messages = []
    for tool_call, result in zip(tool_calls, results):
        if isinstance(result, Exception):
            content = f"工具執行失敗：{str(result)}"
        else:
            content = str(result)

        tool_messages.append(
            ToolMessage(
                content=content,
                tool_call_id=tool_call["id"],
                name=tool_call["name"]
            )
        )

    return {"messages": tool_messages}
```

```text
正在查詢工單系統...    完成（找到 47 筆）
```

這種透明度讓使用者知道每個來源的進度，也更容易發現哪個系統較慢或失敗。

## 企業 AI 的延遲來源

<Accordion title="五大延遲來源">
  | 延遲來源 | 典型耗時 | 優化方向 |
  | --- | --- | --- |
  | LLM 推論 | 1–5 秒 | 使用更快模型、Streaming |
  | 外部 API | 0.5–3 秒/個 | 平行執行、快取 |
  | 資料傳輸 | 視資料量 | 限制欄位與筆數 |
  | 重複查詢 | 累加 | 快取相同參數結果 |
  | 網路延遲 | 50–500ms | 就近部署、CDN |
</Accordion>

## 快取策略

```python
class ToolResultCache:
    def __init__(self, ttl_seconds: int = 300):
        self._cache = {}
        self._ttl = ttl_seconds

    def get(self, key):
        item = self._cache.get(key)
        if not item:
            return None
        result, timestamp = item
        if time.time() - timestamp < self._ttl:
            return result
        return None

    def set(self, key, result):
        self._cache[key] = (result, time.time())
```

## 踩坑筆記

<Warning>
  不是所有工具都適合無條件平行：

  1. 多個工具共用同一 API 的速率限制
  2. 多個工具同時修改同一份資料
  3. 後一步需要前一步輸出
  4. 需要原子性保證的事務操作
</Warning>

<Tip>
  判斷工具是否能平行，可以問：「如果把這些工具呼叫的順序打亂，結果會不一樣嗎？」如果不會，通常就可以平行。
</Tip>

<Info>
  今天只要記住一件事：平行化的前提是任務彼此獨立，而不是所有工具一起呼叫。
</Info>
